# 神眸视频切换首帧观察修复

## 问题现象

打开九轴数据后切换神眸 `mb*.mp4` 视频，界面长时间显示“正在切换视频 · 时间轴暂时冻结”。新视频画面会先播放约 `4s`，随后才暂停并跳回开头。

这不是 VLC 解码神眸视频必须等待的时间，而是首帧初始化状态与双时间轴切换保护之间的事件传递冲突。

## 复现结果

使用正式程序入口和以下神眸分段复现：

```text
I:\8.22-8.26 西南一牛舍\左1\mb00000.mp4
I:\8.22-8.26 西南一牛舍\左1\mb00001.mp4
```

修改前切换 `mb00000 -> mb00001`：

| 项目 | 结果 |
|---|---:|
| VLC 视频输出创建 | 正常 |
| 首帧状态 `_prime_frame_ready` | 一直为假 |
| 强制恢复前最大原始位置 | `4420ms` |
| 切换解除时间 | 约 `5.2s` |
| 最终行为 | 强制跳回 `0ms` |

底层单独打开相同文件时，视频输出约 `0.41-0.52s` 创建，媒体时间约 `0.69-0.88s` 开始推进，证明文件和 VLC 本身不需要等待 `4s`。

## 根本原因

正式程序的媒体时间信号原本只连接到统一的 `_on_media_time` 方法。切换数据或视频源时，双时间轴层为了防止临时播放位置污染九轴时间轴，会显示冻结状态并提前返回：

```text
VLC time_changed
  -> 双时间轴切换层接收
  -> 更新切换中的临时显示
  -> 提前返回，不再传给首帧初始化层
```

上一版首帧修复依赖同一个 `_on_media_time` 链判断“视频输出已创建且媒体时间已经推进”。由于神眸切换期间的时间事件被 UI 层拦截，首帧初始化层始终不知道画面已经播放。

双时间轴层另有一个旧恢复机制，每 `350ms` 检查一次，共 `12` 次。首帧状态无法完成时，它会在约 `4.2s` 后强制解除，因此产生了非常稳定的“先播放约 4 秒，再跳回开头”现象；再加上打开和定位时间，实测总耗时约 `5.2s`。

## 修改方案

首帧初始化层在程序初始化完成后，额外直接订阅媒体引擎的 `time_changed` 信号：

```text
VLC time_changed
  -> 原 UI 时间链：切换期间仍可拦截，保护九轴时间轴
  -> 首帧观察器：独立接收，只判断视频输出和首帧
```

这样既不取消“时间轴暂时冻结”的数据保护，也不会让 UI 的临时事件拦截阻断解码就绪判断。

观察器仍沿用上一版的严格条件：

1. VLC 已进入播放状态；
2. VLC 视频输出数量大于 `0`；
3. 媒体时间已经从 `0ms` 向前推进。

满足后立即暂停并进入原有目标位置恢复流程。普通打开时原 `_on_media_time` 链和直接观察器可能都收到同一事件，但暂停请求有幂等保护，只会执行一次。

## 性能与缓存影响

- 不修改神眸源视频。
- 不生成 MKV、视频副本或新缓存。
- 不增加 FFmpeg/FFprobe 扫描。
- 不增加新的轮询定时器。
- 只增加一个 Qt 信号连接；初始化完成后观察器立即返回，普通播放开销可忽略。
- 切换期间仍冻结九轴时间轴，直到原有初始化和定位流程确认完成。

## 修改文件

- `cowmata_tailring/media/mixins/priming_playback.py`：直接订阅媒体时间信号，使首帧观察绕过 UI 展示层的提前返回。
- `tests/test_priming_position_restore.py`：模拟双时间轴层拦截 `_on_media_time`，验证直接信号仍能完成首帧暂停和位置恢复。

- 首帧定向测试：`10 passed`。
