# 乐橙回调播放流安全交接

## 问题现象

当前乐橙专用播放使用 libVLC `media_new_callbacks` 从原文件按关键帧创建轻量虚拟流。真实文件测试中，第一次或第二次拖动跳转可能让进程直接发生 Windows 原生访问冲突；从乐橙文件切换到相邻文件、后台探测把普通文件媒体升级为回调媒体以及程序退出也使用同一危险释放路径。

## 根本原因

每次跳转会创建一个新的回调媒体。旧实现只向播放器请求暂停，随即执行 `libvlc_media_player_set_media(player, None)`。暂停状态不代表 libVLC 的输入/解码线程已经离开 Python `read` 回调，因此主线程修改媒体指针时可能与旧线程并发访问回调媒体，触发 libVLC 原生崩溃。单纯调用 `stop` 也会在同一生命周期窗口内崩溃。

隔离进程验证表明：必须先关闭旧流文件句柄、恢复旧播放器，并留出已测量的退栈静默期，之后才能安全替换媒体。VLC 会提前把短虚拟段读入缓存，所以“已经读到输入 EOF”并不能证明解码线程已经退出，不能作为释放判据。

## 修改方案

1. 交接时先通过 `DahuaPlaybackStream` 的流锁关闭旧源文件句柄，再短暂恢复旧播放器。
2. 固定保留 250 ms，让旧输入、demux、解码和 ctypes 回调栈退出；真实文件验证中 100 ms 仍可能崩溃，而“恢复旧播放器 250 ms”连续多次跳转稳定。
3. 静默期结束后才执行 `set_media(None)`；如果旧播放器无法恢复，则取消跳转或视频切换并报告错误，不再冒险导致进程崩溃。
4. 后台探测将普通文件媒体升级为乐橙回调媒体时，先暂停普通播放器并应用同一 250 ms 退栈余量。
5. 同一交接同时用于拖动跳转、自动跨 60 秒虚拟段、切换视频和程序关闭。

## 修改文件

- `cowmata_tailring/media/safe_engine.py`：回调媒体替换前的安全交接。
- `tests/test_dahua_stream_handoff.py`：覆盖回调流关闭、旧播放器恢复失败、普通媒体暂停、空闲媒体和无播放器路径。
- `CHANGELOG.md`：记录用户可见稳定性修复。

## 数据和兼容性影响

- 不修改、不删除、不移动原视频，不生成 MKV 或额外媒体缓存。
- 每次乐橙跳转增加约 250 ms 固定交接余量，不顺序扫描文件，也不产生额外磁盘占用。
- 右1、海康和普通视频不使用回调播放流，不进入该握手。
- 若旧 VLC 播放器无法恢复，本次操作会失败并保留进程，而不是进入已知会崩溃的媒体替换路径。

## 已知风险

libVLC 3.x 的回调媒体生命周期没有提供“解码线程已退出”的高级公开信号，输入 EOF 又可能因预读而提前发生，因此只能采用真实机器验证过的 250 ms 静默期。不同硬件或 VLC 版本仍可能需要调整该常量；旧播放器无法恢复时会拒绝操作，避免进入已知危险的 detach 路径。
