# 视频预热后目标位置恢复

## 问题现象

首次打开尚无时间轴缓存的视频时，VLC 会先播放一小段，再自动暂停。暂停后的播放位置可能是 `1.345s`，之后点击播放会从该位置继续，用户无法直接从录像首帧开始检查和标注。

本次复现文件：

`I:\8.22-8.26 西南一牛舍\右3\mb00043.mp4`

实测信息：

| 项目 | 数值 |
|---|---:|
| 文件大小 | `268,435,456` 字节 |
| 校正时长 | `704,425 ms`（`00:11:44.425`） |
| 截图中的暂停位置 | `1,345 ms` |
| 第一个视频包位置 | 文件偏移 `56` 字节 |
| 第一个视频包类型 | 关键帧 |

文件开头已经具备可解码关键帧，因此 `1.345s` 不是源录像缺少开头画面。

## 根本原因

播放器打开视频后需要短暂进入播放状态，以便 VLC 初始化 H.264/HEVC 解码器。海康 MPEG-PS 在时间轴缓存未命中时，还会并行运行 FFprobe 包时间戳扫描。

修改前，自动暂停由“可信时长已经产生”触发，但初始化流程没有保存和恢复原本应停留的位置。因此 VLC 在等待时长扫描期间前进了多少，最后就停在多少：

```text
打开视频
  → VLC 从首帧开始预热播放
  → FFprobe 扫描时间轴
  → 可信时长产生
  → 自动暂停
  → 保留预热播放后的 1.345s
```

时间轴缓存只影响 FFprobe 扫描耗时。缓存命中会让问题不明显，但不能保证严格停在 `0ms`。

## 修改方案

1. 每次成功打开视频时，先保存默认初始化目标 `0ms`。
2. 初始化期间继续屏蔽 VLC 预热产生的临时时间，避免临时位置进入界面状态。
3. VLC 自动暂停且可信时长可用后，在现有初始化完成回调中立即向媒体引擎发送一次 `0ms` 定位。
4. 定位接入现有 UI 定位确认屏障，旧解码器时间不会覆盖目标位置。
5. 连续切换视频时，如果程序已经根据九轴播放头计算出非零同步目标，该目标会覆盖默认 `0ms`，并继续走原有覆盖范围检查和安全定位链。
6. 打开失败或窗口关闭时同步清理新增状态，避免上一个文件的初始化目标泄漏到下一次打开。

修改后事件顺序：

```text
打开视频
  → VLC 预热与 FFprobe 扫描并行
  → 可信时长产生并自动暂停
  → 在原初始化完成回调中定位到目标位置
  → 普通打开停在 0ms；连续切换停在计算出的同步位置
```

## 性能影响

- 不增加新的 FFprobe 扫描。
- 不等待扫描结束后再启动另一个串行任务。
- 不生成 MKV、视频副本或新缓存格式。
- 连续视频切换原本就会执行同步定位，本次没有增加额外定位次数。
- 普通首次打开新增一次异步 `0ms` 定位；该文件首包就是关键帧，不需要向前解码很长的 GOP。
- 不改动现有 `250ms` VLC 解码器交接保护。

因此，切换冻结的主要耗时仍是原有解码初始化和冷缓存时间轴扫描。本次修复恢复正确起点，不增加一个可见的串行等待阶段。

## 修改文件

- `cowmata_tailring/media/mixins/priming_playback.py`：保存初始化目标，区分普通首帧恢复和连续切换同步定位，并在初始化完成时恢复位置。
- `cowmata_tailring/app/mixins/cancel_safe_open.py`：打开失败时恢复新增初始化状态。
- `cowmata_tailring/app/mixins/timer_shutdown.py`：关闭窗口时清除新增初始化状态。
- `tests/test_priming_position_restore.py`：覆盖冷打开回首帧、连续切换保留原定位链和失败回滚。

## 已知限制

- 本次修复保证初始化完成后恢复目标位置，不取消 VLC 为产生首帧而进行的预热播放。
- 冷缓存时，界面仍需等待可信时间轴产生后才能解除时间轴冻结。
- 如需进一步缩短冷切换时间，应另行实现相邻视频时间轴预扫描；该功能不属于本次修改。
- 离屏自动测试不能确认最终显示画面的视觉内容，需要在桌面窗口中人工确认首帧画面。
