# 单路优先与播放性能（3.1.2）

## 推荐怎么用

默认「单路优先」适合笔记本：只有主视角连续播放，其他视角在主路就绪后逐个抽取静止图。鼠标移入画面，出现半透明控制条；移开后收起。

- 点击另一视角的播放键：切换主视角，其余暂停；新画面按当前九轴时刻定位。
- 后退/前进 5 秒、倍速：调整**共用标注时间轴**，不会让各视角各走各的时间。
- 放大/恢复：只改变布局，不改素材或时间。全局播放、逐帧和快捷键仍保留。
- 静止图显示「已暂停」与实际截图时间，不是当前视频真值。暂停标注时，各路依次刷新到同一标注时刻的原片精确帧；缺口明确显示。
- 若需要周期观察辅路，可选「流畅优先」；硬件允许时可选「多路全速」。已有工程尊重保存的偏好；点击任一画面的播放键会切到单路优先。

## 为什么不能只增加 CPU 线程

监控客户端通常把码流、缓冲、解码和渲染分别管理，并使用硬件解码降低高分辨率视频的 CPU 开销。离线内存卡录像不一定有可切换的低清子码流，因此本程序用原片静止图作辅路，不假设存在摄像机直播子码流。[Axis 官方排障说明](https://help.axis.com/en-US/troubleshooting-streaming)

NVIDIA 的视频解码使用专用 NVDEC 单元，不是把普通计算 GPU 使用率拉满。并行解码仍受硬件能力、显存和驱动制约；无需给用户安装 CUDA 工具包。[NVIDIA NVDEC 官方说明](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvdec-application-note/index.html)

本版将原生播放器的打开、跳转和状态读取移到各自的工作线程；只保留最新跳转请求。每路限制 CPU 解码线程，GPU 仍自动尝试；单路优先最多一项后台辅路抽帧。原始帧率、录像字节、九轴 50 Hz 样本不改动，不插帧、不重编码整库。

## 实测口径与结果

2026-09-09，本机 Core Ultra 9 285K / RTX 2080 Ti，Windows，开启完整现代界面与磨砂效果。1000 份合成九轴文件中只选一份一小时、180001 个样本；四份用户提供的真实 H.264/HEVC 录像重复显示成八个视窗，**不是八台独立摄像机**。新建索引，不清操作系统文件缓存；不是冷磁盘或网络盘性能。

第三轮本地测试（在前两轮基础上合并索引建表事务、继续修复原生跳转确认）：

| 项目 | 实测 |
| --- | --- |
| 所选一小时九轴加载 | 0.79 秒 |
| 首张对应录像画面出现 | 2.58 秒 |
| 四份录像候选建立 | 5.93 秒；图像核验继续后台执行 |
| 单路播放期间 GUI 事件队列延迟 P95 / P99 | 3.38 / 5.68 ms |
| 四次切视角按钮回调 | 10.26–12.27 ms |
| 新视角原片解码到位 | 1.49–4.90 秒；界面不等待解码返回 |
| 未读取的其他九轴 | 999 份 |
| 66 秒连续播放、跨内部传输边界、倍速、放大恢复、暂停八路对齐、正常退出 | 通过 |

响应测量是在真实 Qt 事件循环中，由后台线程每约 20 ms 投递事件并记录排队时间，不是将定时器周期当作响应时间。按钮回调耗时、实际画面到位时间分别统计。

**25 ms 不是硬实时保证。** 第三轮单路播放事件样本约 99.84% 在 25 ms 内，最高约 108 ms（包含测试截图）；工程初始化回调约 212 ms、首次创建八个视窗约 379 ms 仍是一次性开销，整个初次准备阶段也有超过 25 ms 的排队尖峰。较慢硬盘、驱动、其他软件负载和未知格式 OCR 会改变结果。本机测得的 P95 不代表每次点击或所有客户电脑的最大延迟。

所有暂停帧检查仍基于原片 PTS；冻结的辅路预览不会进入证据确认。原有自动识别只产生候选，以上性能测试不评价行为识别准确率。
